# 13VT — จุดตรวจสเปกก่อนสัญญารับ/จ่าย USDT จริง

> **ยังไม่ใช่ Smart Contract สำหรับเงิน USDT จริง**: `UnfundedFifoModel.sol` ที่อยู่ข้างไฟล์นี้เป็นสถานะจำลอง ไม่มี `transferFrom`/`transfer`. ห้ามนำ address/ABI ของมันไปแทนสัญญาคิวในเว็บหรือใช้กับเงินจริง

## กฎที่ผู้ใช้ระบุแล้ว (สรุปคำตอบ 2 ต.ค. 2026)

- ฝากครั้งละ 13 USDT; Direct **เลขคี่** ในผัง A เป็นเส้นทางรายได้แก่ผู้แนะนำตรง ตามกฎ A ที่ระบุมาก่อนหน้า ไม่ใช่หมายถึง Direct #4/#6. U1 #2 ในตัวอย่างกันให้ U1 เพื่อจ่ายเมื่อมีลูกซ้าย B; **ผู้ใช้แก้ไขล่าสุดว่า D #2 ไม่กันให้ D** จึงต้องแยกยอด D #2 เป็นเงินอยู่ในสัญญาที่ยังไม่ผูกปลายทาง จนกว่าจะยืนยันกฎใช้ก้อนนี้
- Direct **เลขคู่ #4/#6 เป็นต้นไป** ฝากเงินไว้ **ในสัญญาเพื่อจ่ายออก** (ยังไม่ระบุว่ากันให้ Position A ใหม่ใดหรือจ่ายให้ B parent ใด; ห้ามสรุปเองว่าเป็น Fee Wallet)
- B เป็น FIFO รวมทุก Wallet/Position: Parent เก่าสุดที่ยังมีช่องว่าง, ซ้ายก่อนขวา. U1 ได้รับ 13 USDT จาก reserve ของ U1 เมื่อมีลูกซ้าย, รับครั้งเดียว; เมื่อซ้ายและขวาครบและรับสำเร็จแล้ว สร้าง U2 เข้าคิวทันที
- U2 ที่ไม่มี deposit ของตนแสดง `UNFUNDED`. คำตอบล่าสุดระบุว่าเมื่อ U2 เป็น Parent และลูกจาก Position ที่ผ่าน A ครบ Direct #1/#2 มาต่อ ให้ **วางแล้วโอน B 13 USDT ทันที** โดยอ้างเงินจาก A ที่ผ่านเงื่อนไข ไม่ใช้แบบ Claim; แต่ยังไม่ระบุว่าหักจาก depositId ใด และเป็นจังหวะฝั่งซ้ายอย่างเดียวหรือเมื่อซ้ายและขวาครบ
- ค่าบริการ 0.0013 BNB ส่ง Fee Wallet ตามกฎที่ให้มา; Gas แยกต่างหาก แต่ยังต้องกำหนดว่าธุรกรรมประเภทใดเรียกเก็บค่านี้

## ช่องว่างการบัญชีที่ต้องเลือกก่อนใช้ `SafeERC20.transfer`

**ตัวอย่างตรวจ 13 USDT แต่ละก้อน:** U1/A1/D ผ่าน A คนละ Direct 2 รายการ → 6 deposits = 78 USDT. จ่าย Direct #1 ให้ผู้แนะนำ 3 × 13 = 39; จ่าย U1 จาก reserve U1 เมื่อ A1 มาซ้ายอีก 13 = จ่ายรวม 52; ตามกฎเดิม A1 #2 กัน A1 = 13, แต่ D #2 **ไม่กัน D** = 13 ในสัญญาที่ยังไม่ระบุปลายทาง; U2 = 0. ดังนั้น 78 = 52 + 13 + 13. ถ้าภายหลังยืนยันให้นำ D #2 จ่าย U2 → จ่ายรวม 65, A1 reserve 13, D ไม่มี reserve; บัญชียังสมดุลแต่ **ต้องยืนยันว่า D รับสิทธิ์เมื่อไร**. อย่าจ่าย U2 ก่อนระบุ depositId และ event ที่ผูกอย่างชัดเจน

ถ้า **U2 ที่ UNFUNDED** ได้ลูกจาก Position ใหม่ Q ที่ผ่าน A: Direct #1 ของ Q จ่ายผู้แนะนำ Q. ต้องตัดสินว่า Q #2 จะกันให้ Q เอง, ใช้จ่าย U2 แล้ว Q กลายเป็น `UNFUNDED`, หรือใช้ deposit เลขคู่ก่อนหน้าที่ไม่ถูกผูก (เช่น D #2) ผ่าน FIFO ของเงินแยกต่างหาก. การบันทึกว่า `PAID` โดยไม่ตัดจาก depositId ที่ยังใช้ได้จะสร้างหนี้เกินยอดหรือใช้เงินซ้ำ

ต้องยืนยันเป็นลายลักษณ์อักษรก่อนสร้างสัญญาจ่ายเงินจริง:

1. เงิน B payout ให้ U2 ที่ UNFUNDED มาจาก depositId ของธุรกรรมใด (D #2, คู่ #4/#6 ของใคร หรือ Q #2) และถ้าเงินจาก Q #2 ถูกใช้จ่าย U2, **Q ยังมี reserve อยู่หรือกลายเป็น UNFUNDED**? ข้อความล่าสุดยังไม่เลือกรายการใดแน่ชัด
2. เมื่อมีหลายเงินฝาก #4/#6 อยู่ใน Contract, กฎจับคู่เงินก้อนกับ B parent หัวคิวและการกัน reserve ของ A-position ใหม่เป็นอย่างไร? ใครได้รับค่าธรรมเนียม BNB ทุกกรณี?
3. ผู้ใช้เลือก **BSC Testnet ก่อน** แต่ขณะนี้สั่งให้ **คงเป็น mock ที่ไม่โอนเงินจริงและไม่ Deploy** จึงทดสอบได้ด้วย Remix VM / local EVM โดยไม่ใช้ token address. Address `0x11B948575B648be50Eef781251ebdc876907E618` ที่ให้มาเป็นค่า **Owner wallet** ในเว็บ และ read-only `eth_getCode` บน BSC Testnet (chain `0x61`, ตรวจ 2 ต.ค. 2026) ได้ `0x` — **ไม่ใช่ BEP-20 contract**. หากวันหลังจะทดสอบโทเคนบน Testnet จริง ต้องระบุ address ของโทเคนทดสอบอีกตัว, decimals และตรวจ source ใหม่; ห้ามแทน address Owner เป็น token
4. หากไม่มีเงินที่ยังไม่ผูกพอจ่าย 13 USDT ทันที ธุรกรรมต้อง revert ทั้งหมด, วางแล้วค้าง Pending, หรือมีผู้เติมเงินใหม่อย่างไร? คำตอบ “วางแล้วจ่าย” ต้องมีแหล่งเงินรองรับ ไม่ใช่สร้างเครดิตโดยไม่มีหลักประกัน
5. กำหนดสิทธิ์ผู้แก้ค่าบริการ/ผู้รับ, emergency pause, ถอนเงินส่วนเกิน (ถ้าอนุญาต) และกระบวนการแก้ contract; งดย้าย/ถอน reserve ของผู้อื่นโดยไม่มีสิทธิ์และหลักฐาน

## เกณฑ์ที่สัญญาเงินจริงควรผ่านเมื่อกฎครบ

- ทดสอบ `approve → transferFrom` 13 หน่วยตาม `decimals()` จริง, exact amount received (reject fee-on-transfer/rebase หากรองรับไม่ได้), BNB fee แยก, `SafeERC20`, checks-effects-interactions และ reentrancy guard
- ทดสอบ Direct คี่/คู่ #1–#6, A → B, FIFO ซ้าย/ขวา, U2 `UNFUNDED` ที่มีลูก, เงินสำรองแต่ละ Position, บล็อกเดียวหลายรายการ, refund/revert, receipt/events และการโอนล้มเหลว
- invariant ราย deposit: `deposited = paid + unspent reserve + unallocated`, ทุก payout อ้างเงินที่ไม่เคยจ่าย; รวม reserve ที่ยังไม่จ่ายต้องไม่เกิน `USDT.balanceOf(contract)`
- คอมไพล์/ทดสอบอัตโนมัติ, ฝึกบน local EVM + testnet และตรวจสอบความปลอดภัย/กฎหมายก่อน mainnet; **ไม่มี deployment หรือการเงินเกิดขึ้นจากเอกสารนี้**
